## 命名規則（このログとバックアップ運用のルール）

### バックアップ

- 保管場所：プロジェクト直下 `_backups/`（Gitには含めない。`.gitignore` に追加済み）
- フォルダ名：`YYYYMMDD_HHmmss`（例：`20260922_022900`）
  - 元の提案「修正履歴_yyyymmdd_MM:dd:ss」はコロン（:）がWindowsのファイル名に使用できない文字のため、ハイフン・コロンなしの形に変更
- 中身：修正対象ファイルを、`src/components/Admin.tsx` のように元のディレクトリ構造を保ったまま格納
- 運用：Claudeがソースファイルを修正する前に、その時点の対象ファイルを新しいタイムスタンプフォルダにコピーしてから編集する

### 検討ログ（本ファイル）

- 1ファイルに集約し、日時の新しい順ではなく古い順に追記していく（既存の `docs/00〜11` の番号規則に合わせて `13_` を付与）
- 見出し形式：`## YYYY-MM-DD HH:mm 決定事項のタイトル`
- どのセッション（Claude Code / claude.ai どちらでも）でこのアプリに加えた変更・決定であっても、本ファイルに記載する

### ローテーション（ログが増えすぎないようにする運用）

- 本ファイルの決定事項（`## `見出し）が **20件を超えたら**、古い方から10件を `docs/archive_13_変更履歴/` フォルダへ移動する
- アーカイブファイル名は連番（`01.md`, `02.md`, ...）とし、移動した10件をそのまま古い順で集約する
- 移動時、本ファイルの「命名規則」セクションの直後に「## 過去のログ」を作り、アーカイブファイルへのリンクと期間（例：`[01.md](archive_13_変更履歴/01.md)`（2026-05〜2026-09））を一覧表示する
- 移動後も本ファイル・アーカイブファイルとも見出し形式・古い順の並びは変えない

## 2026-09-24 調整機能：名前照合ロジックを2段階構成で確定

- 当初「送信後、名前を完全一致（空白正規化）で自動判定し、一致すれば既存アカウントへ無条件に反映する」という案を提示したが、「別人だった場合に困る」との指摘を受け再検討
- 目的の異なる2つの照合を明確に分離する構成に修正して確定
  - **第1段階：イベント内の重複チェック**（要件「名前の重複は基本認めない」に対応）。今回の調整対象（`chouseisanEntries`）内で正規化名（前後空白除去＋全角/半角スペース統一）が既に存在するか確認する
  - **第2段階：正規部員照合**（要件「正規部員として登録済か照合」「登録済なら本人として」「未登録ならゲスト」に対応）。同じ正規化ロジックで`users`（正規部員名簿）と完全一致照合し、一致すれば正規部員としてレベル上書きなしで反映、一致しなければゲストとして扱う（単一日程モードは即時ID発行、複数候補日モードは仮ID発行）
- 第1段階について、当初は「完全一致なら自動的に上書き」としていたが、以下の経緯で確認ポップアップ方式に変更
  1. 「一致したら無条件に上書き」は、別人が同じ名前で回答した場合に他人の回答を破壊してしまう恐れがあると指摘を受けた
  2. 対応として「同姓同名の回答が既にあるため上書きになります。よろしいですか？」というポップアップを出し、「はい」なら既存回答を上書き、「いいえ」なら別人として新規保存する案を提示
  3. この案について、「いいえ」を選んだ場合に同名2件が残ってしまい、その後の会員照合（第2段階）でどちらの行を本人に紐付けるか機械的に判定できなくなる問題を指摘。また「同姓同名の回答が既にある」という情報自体の開示が新たな情報漏えいにならないか論点として提示したが、「一覧を確認すれば分かることなので問題に当たらない」との判断で合意
  4. 「いいえ」を選んだ場合の扱いについて3案（A：区別用の識別子を付けて別行保存し、管理画面に「同姓同名あり・要確認」として表示、最終判断は管理者が手動で行う／B：機械的に先着1件のみ正規部員に紐付け、2件目はゲスト扱いに固定／C：「いいえ」の選択肢自体を用意せず常に上書きに統一）を提示し、**A案を採用**
  5. 採用理由：同姓同名は実際にはほとんど発生せず、発生しても漢字表記の違い等ですぐ判別できるため、稀に発生した場合のみ管理者が手動で解決すれば十分という判断（「基本認めない」の「基本」は同姓同名が存在しない前提であり、存在する場合は例外として認めるほかない、という整理）
